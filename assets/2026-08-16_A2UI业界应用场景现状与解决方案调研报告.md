# A2UI 业界应用场景现状与解决方案调研报告

> 调研时间：2026 年 8 月
> 覆盖范围：A2UI（Agent-to-User Interface）协议的定义、技术原理、生态定位、应用场景现状、解决方案全景与趋势判断

---

## 一、结论速览（TL;DR）

**A2UI（Agent-to-User Interface）是 Google 于 2025 年 12 月开源并主导的「声明式 UI 协议」**，它让 AI Agent 不再只输出文字，而是输出一份描述 UI 结构的 JSON 蓝图，由宿主应用用自带的原生组件渲染成可交互界面。

- **要解决的问题**：AI Agent 如何**安全地**跨信任边界给用户生成**富交互界面**——既不退回到效率低下的纯文本聊天，也避免让 LLM 直接生成可执行 HTML/JS 代码（存在 XSS 等安全风险）。
- **核心创新**：①「邻接表」扁平组件模型（降低 LLM 生成难度、原生支持流式增量渲染）；②「组件目录协商」机制（Agent 只能使用客户端预批准的组件，实现"像数据一样安全、像代码一样丰富"）。
- **生态定位**：它是 AI Agent 协议栈中面向「界面内容」的一层，与 MCP（工具层）、A2A（协作层）、AG-UI（交互传输层）**互补而非竞争**。
- **成熟度**：2026 年 4 月发布 v0.9，仍处**早期公开预览**阶段；但其背后有 Google、CopilotKit、Flutter 等重磅力量押注，被视为"2025 年大模型最重要的体验更新"、对话式 AI 走向大众的"最后一公里"。
- **垂直场景延伸**：除通用 AI 界面外，A2UI 及其范式在**教育（个性化教学/在线课堂）、会议（智能纪要/可视化答疑）、投屏大屏（数据墙→实时交互体）**等场景均有落地探索（详见第六章补充）。
- **硬件承载终端**：华为 **IdeaHub** 智慧屏（HarmonyOS 大屏 + 白板 + 多模态交互 + OPS 生态）可作为 A2UI 动态界面在教育/会议/大屏场景的硬件级落地方案（详见 6.5）。

**一句话判断**：A2UI 是"把 8 轮对话压缩成 3 次点击"的交互代际跃迁的技术底座，正从概念验证走向工程落地。

## 二、A2UI 是什么

### 2.1 一句话定义

> **A2UI 是一种声明式的生成式 UI 规范，允许 AI Agent 用 JSON 数据描述 UI 的布局与组件，客户端用本地已有的组件库把它渲染成可交互界面。**

A2UI 的官方核心表述：

- 让 AI Agent **跨 Web、移动端、桌面端原生渲染**丰富交互界面，**无需执行任意代码**。
- 设计哲学：**"像数据一样安全，像代码一样丰富。"**
- 本质是一份"通用 UI 语言"——Agent 说这种语言，客户端用自己能理解的方式渲染。

### 2.2 与传统方案的本质区别

| 方案 | 安全性 | 表达力 | LLM 生成友好度 |
|------|--------|--------|----------------|
| 纯文本对话 | ✅ 高 | ❌ 低（多轮低效） | ✅ 高 |
| 直接生成 HTML/JS 代码 | ❌ 低（XSS/任意代码风险） | ✅ 高 | ⚠️ 中 |
| **A2UI（声明式 JSON）** | ✅ 高（组件白名单） | ✅ 高（富交互） | ✅ 高（扁平流式） |

### 2.3 一个直观对比：订餐厅

**传统聊天式 AI**（8 轮对话、2 分钟、体验差）：

```
你：帮我订明天晚上7点的餐厅 → AI：请问几位？→ 你：2位 → AI：偏好菜系？
→ 你：意大利菜 → AI：以下是餐厅列表，选哪家？→ 你：第2家
→ AI：7点没位置，有6:30和8:00 → 你：8:00 → AI：姓名和手机号？
→ 你：张三，138xxx → AI：预订成功！
```

**A2UI 方式**（1 个界面、10 秒、3 次点击）：Agent 直接生成一张带日期选择器、时间下拉框、人数选择、餐厅卡片列表、预订按钮的表单，用户点点点即完成。

> 这正是 A2UI 的价值主张——**把"AI 会说话"升级为"AI 会做事"**。

## 三、技术原理与核心创新

### 3.1 三层解耦架构

| 层级 | 说明 | 由谁提供 |
|------|------|----------|
| **组件树（Structure）** | 抽象 UI 结构描述 | Agent |
| **数据模型（State）** | 动态填充 UI 的应用状态 | Agent |
| **组件目录（Catalog）** | 可信组件映射表（白名单） | Client 定义 |

- **安全性**：Agent 只能用客户端预定义组件，无法注入代码。
- **灵活性**：同一份 UI 描述可在 Angular/React/Flutter/原生移动端渲染。
- **高效性**：数据变化无需重发整个 UI 结构。

### 3.2 关键创新一：邻接表模型（vs 嵌套树）

A2UI 采用**扁平邻接表**而非传统嵌套 JSON 树，这是针对 LLM 的刻意设计：

| 特性 | 嵌套树（如 Adaptive Cards） | 邻接表（A2UI） |
|------|------------------------------|----------------|
| LLM 生成难度 | 高（需一次性正确嵌套） | 低（逐个组件生成） |
| 增量更新 | 困难 | 简单（按 ID 更新） |
| 流式传输 | 不支持 | 原生支持 |
| 错误恢复 | 整体失败 | 单组件失败不影响其他 |
| 数据/结构 | 耦合 | 分离 |

### 3.3 关键创新二：组件目录协商（安全核心）

```
① Agent 在 Agent Card 中声明支持的目录
② Client 在每条消息中声明自己支持的目录（可含自定义内联目录）
③ 双方取交集，Agent 只能使用交集中的组件
```

配合四层防护约束 LLM：**JSON Schema 强约束 → Prompt 组件目录 → 协议层目录协商 → 渲染层组件白名单**。未知组件被忽略/占位/报错，不执行任意逻辑。

### 3.4 消息类型与数据流

五种核心消息：`surfaceUpdate`（定义结构）、`dataModelUpdate`（填充数据）、`beginRendering`（触发渲染）、`deleteSurface`（清理）、`userAction`（用户操作回传 Agent）。

数据流：用户请求 → Agent 调用 LLM → 生成 A2UI JSON（JSONL 流）→ 经 SSE/WebSocket/A2A 传输 → 客户端原生组件渲染 → 用户交互经 userAction 回传 → Agent 处理业务逻辑。

### 3.5 标准组件目录（v0.8/v0.9）

- **布局**：Row、Column、List
- **展示**：Text、Image、Icon、Video、AudioPlayer、Divider
- **交互**：Button、TextField、CheckBox、DateTimeInput、Slider、MultipleChoice
- **容器**：Card、Tabs、Modal
- 支持**动态列表模板**（`template` + `dataBinding`）与**自定义组件扩展**。

### 3.6 职责边界

| A2UI 负责 | A2UI 不负责 |
|-----------|-------------|
| UI 结构描述、数据绑定、交互事件传递、渲染控制 | 业务逻辑执行、外部 API 调用、数据持久化、身份认证 |

业务逻辑由 Agent 通过内置 Tools、MCP 服务器、A2A 委托、直接 HTTP/gRPC 实现。

## 四、生态定位：与 MCP / A2A / AG-UI 的关系

2026 年 AI Agent 生态迎来"协议爆发"，四个协议各自解决不同层次的问题，**是叠加而非竞争**：

| 协议 | 创建者 | 解决的问题 | 协议层次 | 类比 | 成熟度 |
|------|--------|-----------|----------|------|--------|
| **MCP** | Anthropic | Agent ↔ 工具/数据 | 工具层 | 办公工具 | ⭐⭐⭐⭐⭐ |
| **A2A** | Google | Agent ↔ Agent 协作 | 协作层 | 部门协作 | ⭐⭐⭐⭐ |
| **AG-UI** | CopilotKit | Agent 后端 ↔ 前端实时交互 | 交互层 | 客户电话 | ⭐⭐⭐ |
| **A2UI** | Google | Agent → 生成 UI 组件 | **UI 层** | 报价单模板 | ⭐⭐ |

**一句话区分（最易混淆的 AG-UI vs A2UI）**：
- **AG-UI 是"管道"**——负责事件怎么从后端传到前端（SSE 事件流）。
- **A2UI 是"包裹"**——负责传过去的 UI 长什么样（声明式 JSON 组件蓝图）。
- 二者**互补**：A2UI 生成的 UI 蓝图可经由 AG-UI 的事件流传输。CopilotKit 深度参与 A2UI 设计，具备 **Day-Zero 兼容**。

**网络协议类比**：MCP≈网卡驱动、A2A≈TCP、AG-UI≈HTTP、A2UI≈HTML/CSS。

**技术演进脉络**：AI 交互经历了 **固定 UI（输入框+聊天气泡）→ 意图驱动的动态生成界面（AG-UI/A2UI）** 的转变，未来 AI 应用可能不再有固定界面，而是按每次交互需求动态组装组件。

## 五、应用场景现状

A2UI 的应用场景可归纳为六大类，均已出现官方 demo 或行业落地探索。

### 5.1 动态数据收集（动态表单生成）

替代传统多轮文本问答，Agent 根据上下文动态生成定制化表单。

- **典型场景**：预订系统、调查问卷、订单填写、生日派对场地预订、需求采集。
- **案例**：用户说"我要预订生日派对场地"，Agent 自动生成含**日期选择器、人数滑块、预算区间、特殊要求输入框**的原生表单，直接填写提交，无需低效文本往返。

### 5.2 AI Agent 富交互界面（从"聊天"到"界面"）

这是最基础也最普遍的场景——AI 输出从"一段话"变成"个性化 App 与文字的混合体"。

- **天气**：不再说"明天 25 度晴"，而是直接画一张**天气卡片**。
- **订餐厅/订票**：直接弹出**日期选择器 + 时间下拉框 + 确认按钮**。
- **数据分析**：不甩数字，生成**可交互图表/仪表盘**。

### 5.3 远程子智能体协作（多 Agent 统一门面）

主智能体将任务委派给远程专业智能体，并把子 Agent 返回的 UI 负载直接嵌入主界面。

- **旅行预订**：主 Agent 委派航班搜索给专业旅行 Agent，子 Agent 返回**航班卡片、排序下拉框、预订按钮**的 UI 描述，主界面直接原生渲染，用户无需离开当前对话窗口。
- **意义**：不同来源的 AI 生成**风格统一**的界面，解决多 Agent 返回割裂格式的痛点。
- **适用**：企业级多智能体系统、专业领域 AI 助手、跨组织智能体协作。

### 5.4 企业审批工作流 / 数据分析可视化

Agent 动态生成审批仪表板、数据图表、可交互报表和操作按钮。

- 智能体根据查询动态生成审批界面，用户用原生 UI 组件**查看数据、批准/拒绝请求、添加备注**，工作流可视化不再是"聊天"。
- **适用**：企业资源管理、财务审批、项目管理系统、数据分析仪表板。
- **官方案例 RizzCharts**：AI 驱动的电商仪表板，含交互式圆环图、地图、条形图，支持悬停查看详情、向下钻取、过滤时间范围——证明 A2UI 能支撑复杂数据可视化。

### 5.5 跨平台 UI 渲染（Write Once, Render Everywhere）

同一份 JSON 蓝图可在 Web（Angular/React/Lit）、移动端（Flutter/SwiftUI/原生）、桌面端（Electron）渲染。

- 网页 → React 组件；iOS → SwiftUI 视图；Android → Flutter 界面。
- **意义**：打破平台壁垒，一套 Agent 输出全端可用。

### 5.6 新兴/前瞻场景

- **AI Mini App**：Google 内部已在探索，Agent 生成轻量小应用。
- **车载交互 / 游戏场景**：行业讨论中提及，Agent 驱动的动态界面可提升车载 HMI 与游戏内交互体验。
- **个人化 UI 生成**：如用户上传景观照片，Agent（Gemini）理解后生成**定制化需求表单**（保留橡树？[是/否]、预算范围[滑杆]、风格偏好[现代/田园]）。

## 六、补充场景：教育 / 会议 / 投屏大屏

> 这三类场景是 A2UI 及其代表的"Agent 驱动动态 UI"范式在**具体垂直行业**的落地切片。它们既体现 A2UI 协议本身的能力边界，也展示了与之相关的商业解决方案如何在实际业务中兑现价值。其中**投屏大屏**场景尤其与 A2UI 的"运行时动态生成界面 + 流式渲染"能力高度契合。

### 6.1 教育场景

教育是 A2UI"动态表单 + 富交互界面"能力的天然应用土壤——学习过程天然需要结构化输入、即时反馈与个性化适配，而这正是纯文本对话的短板。

**核心应用方式**（基于 A2UI 动态 UI 生成能力）：

| 能力 | 说明 |
|------|------|
| **交互式练习题与测验** | Agent 根据学习内容动态生成单选/多选/填空/滑块等题型，替代静态题库，按学生掌握程度实时调整难度 |
| **多媒体教学内容展示** | 动态组合文本、图片、视频、音频播放器，将知识按需组织成富媒体卡片 |
| **学习进度跟踪与反馈** | 动态生成进度条、状态指示器、成绩统计图表，即时呈现学习成果 |
| **个性化学习路径推荐** | 根据学生答题数据，Agent 动态生成下一步学习内容与推荐清单 |

**落地方向与价值**：
- **在线课堂/教学平台**：课件不再"千人一面"，Agent 按学生画像动态组装教学界面。
- **课后辅导/练习系统**：把"多轮问答式刷题"压缩为"一页可视化练习界面"，一次生成整套题型，学生直接在原生组件上作答，答题数据实时回传 Agent 生成下一题。
- **远程培训**：参考会议场景中的培训用例，AI 自动整理课程重点、生成练习题、统计疑问点、批改作业（效率提升约 60%）。

> **A2UI 价值点**：动态表单收集（答题/输入）+ 富媒体展示（多媒体课件）+ 数据可视化（进度/统计）+ 个性化推荐，四者正是 A2UI 四大核心场景在教育端的映射。

### 6.2 会议场景

会议是"多轮低效对话"痛点最集中的办公场景之一，也是 A2UI 及"智能会议 Agent"方案落地最成熟的领域。业界已有腾讯会议 AI 小助手、飞书智能会议纪要、Zoom AI Companion 等成熟产品，其共性趋势是**从"静态纪要"走向"动态可视化交互界面"**。

**智能会议 Agent 的完整能力（会前—会中—会后全流程）**：

| 阶段 | 能力 | A2UI 界面呈现方式 |
|------|------|------------------|
| **会前** | 自动提醒参会、同步会议资料 | 动态生成参会清单、资料卡片列表 |
| **会中** | 实时录屏 + ASR 转写（准确率 98%+）、声纹识别说话人、OCR 识别 PPT/白板、智能答疑、动作项自动标记 | 实时滚动纪要、说话人标注、答疑卡片、动作项打标列表 |
| **会后** | 1 分钟内生成分模块纪要、动作项自动同步到多维表格、资料归档、主动跟进提醒 | 结构化纪要页面、动作项责任人与截止时间看板、待办清单 |

**关键创新点（与 A2UI 范式的结合）**：
- **多模态感知 → 动态 UI**：ASR 语音转写、OCR 识别共享屏幕（PPT/白板）、声纹分离说话人，这些结构化信息正是 A2UI 数据模型（dataModelUpdate）的输入源。
- **对话式问答 → 界面化呈现**：参会人通过提问接口（如 `/api/meeting/ask`）向助手提问，助手不再只回文字，而是动态生成**可视化答案界面**（数据图表、关联文档卡片、动作项清单）。
- **主动式 UI 更新**：识别到"下周一张三提交方案"这类动作项后，Agent 到时间自动向界面推送更新的待办清单——对应 A2UI 的增量式 `surfaceUpdate`。

**落地收益**：企业内部日常例会后整理时间从 2.5 小时降至 1 分钟，全公司每周节省超 1000 小时；面试场景效率提升 50%；线上发布会自动整理问答集锦。

> **说明**：会议场景中"动态生成可视化界面"的底层能力，与 A2UI 的目标（让 Agent 输出富交互界面而非纯文本）高度一致。当前多数会议产品先以"文字纪要 + 表格"形式呈现，向 A2UI 标准的动态界面演进是其自然延伸。

### 6.3 投屏 / 大屏场景

投屏大屏场景与 A2UI 的**"运行时动态生成界面 + 流式渲染 + 跨平台原生组件"**能力契合度最高，是 A2UI 最具差异化的应用方向之一。业界正推动大屏从**静态数据墙**升级为**实时交互体**。

**传统大屏的痛点 vs 智能交互大屏（Agent + 动态 UI）**：

| 维度 | 传统静态数据大屏 | 智能交互大屏（Agent + 动态界面） |
|------|------------------|-----------------------------------|
| 交互方式 | 单向展示、"被动看数据" | "随问随答、主动聊数据"，语音/触控交互 |
| 内容生成 | 开发期写死模板 | Agent 按场景/查询**动态组装界面** |
| 数据可视化 | 固定图表 | 按数据类型自动选图（柱状/折线/饼图）+ 实时更新 |
| 场景适配 | 单一模板 | 常规运营/营销活动/销售淡季/特殊事件一键切换 |
| 响应能力 | 刷新慢 | 端侧渲染，端到端 ≤500ms，弱网可用 |

**核心落地方式**：
- **端侧 Agent + 端侧渲染**：仅传输 KB 级轻量驱动指令（而非完整视频流），场地终端本地渲染，弱网稳定、低延迟（≤500ms）、云端零算力成本。
- **数字人播报 + 动态 UI**：数字人结合 TTS 自动播报数据洞察，界面同步生成可视化图表与场景卡片。
- **智能问答界面**：访客/运营人员提问（如"今年增长情况？"），Agent 动态生成数据图表 + 文字解读的混合界面，流式输出（SSE 打字机效果）。
- **降级机制**：AI 调用失败时自动切换到基于规则的增强生成器，保证大屏服务不中断。

**典型应用场所**：
- **企业展厅**：访客进入即自动介绍企业运营数据，随问随答，提升参观体验。

- **会议/报告投屏**：投屏内容不再固定为静态 PPT，可随讲解进程由 Agent 动态生成与切换界面。

> **A2UI 契合点**：大屏场景强调"同一份 UI 描述跨 Web/大屏/触屏一体机渲染 + 流式渐进式构建 + 组件白名单安全"——这正是 A2UI"Write Once, Render Everywhere"与渐进式渲染的用武之地。相比手机端，大屏的**大尺寸、多人围观、强视觉化**特性更能放大 A2UI 动态组件的价值。

## 七、解决方案全景

A2UI 的"解决方案"可分两条线：**协议标准/开源方案**（解决"底层怎么造界面"）与**商业生成式 UI 工具**（解决"开发者怎么用 AI 造界面"）。

### 7.1 协议标准与开源实现（"AI 自己造界面"）

| 方案 | 说明 |
|------|------|
| **A2UI 规范 + GitHub 官方仓库** | Google 主导、Apache 2.0，含规范、渲染器、传输层实现 |
| **官方客户端渲染器** | Angular、Flutter 等；社区贡献 React 等（框架无关） |
| **传输层** | 支持 SSE/WebSocket/A2A，与 AG-UI 兼容 |
| **A2UI Composer / Widget Builder** | CopilotKit 提供的可视化构建器 |
| **RizzCharts** | Google 官方数据可视化示例 |
| **A2UI 0.9** | 2026 年 4 月发布，提供"共享 Web 核心"，进一步标准化 |

### 7.2 商业生成式 UI 工具（"帮开发者造界面"）

这是更成熟、更贴近开发日常的一条线，核心是 **AI 生成前端代码**（Text/截图/Figma → React/Tailwind 生产级代码）：

| 工具 | 厂商 | 能力 |
|------|------|------|
| **v0 / v0.app** | Vercel | 文本/截图/Figma → 基于 shadcn/ui + Tailwind 的生产级 React 组件与全栈应用，支持 Svelte 等 |
| **Screenshot to Code** | 社区/开源 | 上传截图 → 还原前端代码 |
| **Bolt/Lovable 等全栈生成器** | 各厂商 | 自然语言描述 → 可上线完整应用（与 v0 同赛道竞品） |

> **关键区分**：商业生成式 UI 工具（v0 等）产出的是**可执行的开发代码**，面向"开发者快速造界面"；而 A2UI 协议产出的是**声明式 JSON 蓝图**，面向"AI Agent 在运行时动态给用户生成界面"。前者是**开发时**（build-time）效率工具，后者是**运行时**（runtime）交互范式——两者互补，共同构成 A2UI 领域的完整图景。

### 7.3 集成参考：四协议协同架构

一次完整请求的技术栈（动态 UI 生成应用）：

```
用户点击"查询订单"
  ↓ AG-UI（RUN_STARTED）
  ↓ MCP（调用订单数据库）
  ↓ A2A（委派物流 Agent）
  ↓ MCP（物流 Agent 调用快递 API）
  ↓ A2A（返回结果）
  ↓ A2UI（生成订单详情+物流时间线 UI 蓝图）
  ↓ AG-UI（流式推送 STATE_DELTA）
  ↓ 前端渲染 → 用户看到订单状态和物流时间线
```

## 八、当前挑战

1. **成熟度低**：处于 v0.8/v0.9 公开预览阶段，规范和实现仍在演进，预期会有变化。
2. **渲染器生态待完善**：官方渲染器以 Angular、Flutter 为主，React 等主流框架主要靠社区，跨框架一致性待验证。
3. **协议竞争/混淆**：A2UI、AG-UI、MCP Apps、Adaptive Cards 等方案并存，选型存在认知门槛（MCP Apps 是"外部 iframe 完整体验"，A2UI 是"宿主控制样式的原生组件"，定位不同）。
4. **工程化不足**：动态 UI 与业务逻辑、状态管理、无障碍、主题一致性的深度集成仍需实践沉淀。

## 九、趋势判断与建议

### 趋势判断
- **A2UI 是"大模型 2025 年最重要的体验更新"**：它把 AI 从"对话伙伴"变为"界面设计师"，从"给答案"变为"给结果和工具"。
- **交互范式代际跃迁**：AI 产品形态正从"聊天框 + 固定 UI"走向"运行时动态生成 UI"，AI 应用可能不再有固定界面。
- **生态信号明确**：Google、CopilotKit、Flutter 同时押注；CopilotKit（AG-UI 创建者）参与 A2UI 设计，具备 Day-Zero 兼容——标准收敛趋势明显。
- **对从业者的影响**：前端开发者工作从"实现设计稿"转向"设计可供 AI 调用的组件库"；产品经理需重新思考 AI 产品形态，聊天界面可能不再是最优解。

### 落地建议
1. **从 MCP 开始，按需叠加**：不需要一开始就上全四层协议，按"动态 UI 生成"需求逐步引入 A2UI。
2. **重组件目录设计**：A2UI 时代，组件的**可组合性、语义化程度**成为新核心竞争力——优先沉淀高质量原生组件库。
3. **关注安全模型**：充分利用"组件目录协商"机制，把动态 UI 的信任边界牢牢控制在宿主侧。
4. **试点场景选择**：优先在"动态数据收集、审批工作流、数据分析可视化"等结构化、富交互场景落地验证。
5. **提示词工程调优**：大型 Catalog（50+ 组件）可能导致 LLM 选错组件，建议按场景拆分子目录、在 system prompt 中注入清晰的组件语义描述（详见第十章）。

## 十、技术深度：大模型如何理解与实现 A2UI

> 本章回答三个核心问题：**① 大模型如何"理解"A2UI 范式并生成合规 UI？② 如何实现自定义风格或控件？③ 控件被触发后，后台逻辑如何响应？**

### 10.1 大模型如何理解 A2UI 范式

#### 10.1.1 核心前提：JSON Schema 是 LLM 的"母语"

A2UI 的设计哲学基于一个关键判断——**LLM 天然能理解 JSON Schema**，因此不需要跨客户端标准化组件，而是让 LLM 为每个前端"解读"该前端自己的目录 Schema。

> 官方原话："LLM 可以为每个单独的前端解释目录。"

这意味着：大模型理解 A2UI 不是靠"学习 A2UI 这个框架"，而是靠**读取一份 JSON Schema 文件**——这份 Schema 用标准的 JSON Schema（draft 2020-12）描述了"有哪些组件、每个组件有哪些属性、哪些必填"。

#### 10.1.2 LLM 友好的四大设计

| 设计 | 为什么对 LLM 友好 |
|------|-------------------|
| **扁平邻接表**（非嵌套树） | LLM 逐个组件生成即可，无需一次性构造完美的嵌套层级；出错时只影响单个组件 |
| **基于 ID 的引用** | 组件间通过 `id` 字符串引用父子关系，LLM 只需维护一张"ID 表"，纠正错误时按 ID 定位 |
| **可流式 JSONL 格式** | 每条消息独立一行，LLM 边生成边输出，客户端边渲染（渐进式） |
| **结构化输出**（Structured Output） | 天然适配 GPT-4 / Gemini 的"强制输出符合 Schema 的 JSON"能力 |

#### 10.1.3 Agent 端如何让 LLM 生成 A2UI

**核心机制：将组件目录 Schema 注入 LLM 的 System Prompt。**

```python
# 1. 加载组件目录（JSON Schema 文件）
my_catalog = CatalogConfig.from_path(
    name="my-app",
    catalog_path="file:///path/to/catalog.json",
)

# 2. Schema Manager 自动生成系统提示词（A2UI 指令自动注入）
schema_manager = A2uiSchemaManager(version="0.9", catalogs=[my_catalog])
system_instruction = schema_manager.generate_system_prompt(
    role_description="你是一个餐厅推荐助手，用 A2UI 组件展示推荐结果。"
)

# 3. LLM 接收带目录约束的 prompt，输出符合 Schema 的 JSONL
agent = LlmAgent(
    name="restaurant_finder",
    model="gemini-2.5-flash",
    instruction=system_instruction,  # ← 目录 Schema 在这里注入
)
```

**LLM 实际"看到"的 prompt 包含**：
- A2UI 协议规则（邻接表结构、消息类型、ID 引用规则）
- 组件目录全文（每个组件的名称、描述、属性、类型、必填项）
- 数据绑定规则（`literalString` 字面值 vs `path` 数据路径）
- 输出格式要求（JSONL 流，每行一条消息）

LLM 基于这些约束，**像调用函数一样"选用"组件并填充属性**，输出形如：

```jsonl
{"createSurface":{"surfaceId":"booking","catalogId":"basic"}}
{"updateComponents":{"surfaceId":"booking","components":[
  {"id":"title","component":"Text","text":"预订餐桌","variant":"h1"},
  {"id":"submit-btn","component":"Button","text":"确认","action":{"name":"confirm_booking"}}
]}}
{"beginRendering":{"surfaceId":"booking","root":"title"}}
```

#### 10.1.4 四层约束保障 LLM 输出质量

```
LLM 层    →  Structured Output / JSON Schema 强制输出
Agent 层  →  Prompt 包含完整组件目录 + 语义描述
协议层    →  目录协商（客户端只接受白名单内的组件）
渲染层    →  客户端 WidgetRegistry 只渲染已注册组件
```

**两阶段验证**：

| 阶段 | 位置 | 作用 |
|------|------|------|
| **阶段 1：Agent 端发送前验证** | Agent 侧 | 针对目录 Schema 验证生成的 JSON，捕获幻觉属性/畸形结构；失败可重试或降级为纯文本 |
| **阶段 2：客户端接收后验证** | Client 侧 | 针对本地目录验证，防止版本不匹配；失败时发回 `VALIDATION_FAILED` 事件，Agent 可自我纠正 |

**优雅降级**：

| 场景 | 客户端行为 |
|------|-----------|
| 未知组件（Schema 有定义但渲染器未实现） | 渲染通用卡片占位符或跳过 |
| 未知属性 | 安全忽略，渲染标准组件 |
| 整个 surface 无法渲染 | 显示文本描述或通用错误消息 |
| 验证失败 | 向 Agent 发 `VALIDATION_FAILED`，Agent 收到后可重新生成 |

```json
{
  "version": "v0.9",
  "error": {
    "code": "VALIDATION_FAILED",
    "surfaceId": "flight-status-card",
    "path": "/components/FlightCard/flightNumber",
    "message": "Missing required property 'flightNumber' in component 'FlightCard'."
  }
}
```

### 10.2 如何实现自定义风格或控件

#### 10.2.1 两种自定义策略

| 策略 | 适用场景 | 工作量 |
|------|----------|--------|
| **使用基础目录（Basic Catalog）** | 新应用原型、概念验证 | 低（假设渲染器已存在） |
| **定义自己的目录** | 生产应用、反映现有设计系统 | 中等 |
| **混合方式**（扩展基础目录） | 成熟前端添加 A2UI 能力 | 中等 |

#### 10.2.2 目录 Schema 结构（自定义的"契约"）

目录是一个 JSON Schema 文件，定义**组件、函数、主题**三部分：

```json
{
  "catalogId": "https://example.com/catalogs/my-app/v1/catalog.json",
  "components": {
    "MyChart": {
      "type": "object",
      "description": "交互式图表组件，支持柱状图和折线图",
      "properties": {
        "chartType": { "type": "string", "enum": ["bar", "line"], "default": "bar" },
        "data": { "type": "array", "description": "图表数据点" },
        "title": { "type": "string" }
      },
      "required": ["data"]
    }
  },
  "functions": [ ... ],
  "theme": {
    "primaryColor": { "type": "string", "default": "#1890ff" },
    "borderRadius": { "type": "number", "default": 8 }
  }
}
```

> **关键约束**：目录必须是**独立的**（不引用外部文件），以简化 LLM 推理。开发期可用 `$ref` 模块化，发布前用 `assemble_catalog.py` 工具打包成单文件。

#### 10.2.3 扩展基础目录的三种方式

**方式一：全量导入**（继承所有基础组件 + 新增）

```json
{
  "components": {
    "allOf": [
      { "$ref": "basic_catalog_definition.json#/components" },
      {
        "SuggestionChips": {
          "type": "object",
          "description": "建议提示词列表",
          "properties": { "suggestions": { "type": "array" } },
          "required": ["suggestions"]
        }
      }
    ]
  }
}
```

**方式二：挑选导入**（只继承 Text + 新增 Popup）

```json
{
  "components": {
    "allOf": [
      { "$ref": "basic_catalog.json#/components/Text" },
      { "Popup": { "type": "object", "properties": { "text": { "type": "string" } } } }
    ]
  }
}
```

**方式三：完全自定义**（不继承基础目录，从零定义）

#### 10.2.4 客户端实现渲染器（让自定义组件"活"起来）

目录只定义"Schema 契约"，真正的渲染逻辑在客户端。以 React 为例：

```tsx
// 1. 组件目录映射：A2UI 组件名 → React 组件
const componentCatalog = {
  // 标准组件
  Text: ({ text, variant = 'body' }) => {
    const Tag = variant.startsWith('h') ? variant : 'p';
    return <Tag className={`text-${variant}`}>{text}</Tag>;
  },

  // 自定义组件：交互式图表
  MyChart: ({ chartType = 'bar', data, title }) => (
    <div className="chart-container">
      {title && <h4>{title}</h4>}
      <ECharts option={{ xAxis: { type: 'category' }, series: [{ type: chartType, data }] }} />
    </div>
  ),

  // 自定义组件：带 action 的按钮
  Button: ({ text, variant = 'primary', action }) => (
    <button
      className={`btn btn-${variant}`}
      onClick={() => action?.event && handleAction(action.event)}
    >
      {text}
    </button>
  ),
};

// 2. 用 A2UIProvider 注入目录
<A2UIProvider catalog={componentCatalog}>
  <SurfaceRenderer surface={surface} />
</A2UIProvider>
```

> **安全要点**：自定义组件的**实现代码在客户端侧**，Agent 只能传递数据参数，无法注入逻辑。这正是"像数据一样安全"的保证。

#### 10.2.5 自定义风格（主题/样式）

A2UI 的风格控制权**完全在客户端**：

| 维度 | 实现方式 |
|------|----------|
| **应用样式继承** | 客户端用原生框架（React/Angular/Flutter）渲染，UI 自动继承宿主应用的 CSS/主题 |
| **设计系统对齐** | 在目录 `theme` 字段定义主题变量（颜色、圆角等），客户端渲染时读取并应用 |
| **品牌一致性** | 同一份 A2UI JSON 在不同客户端渲染为各自品牌风格——Agent 不关心样式，只描述结构 |
| **无障碍** | 原生组件自带无障碍特性，无需额外处理 |

> 这意味着：**Agent 永远不会"指定按钮是蓝色还是红色"**——它只说"我需要一个按钮"，颜色由客户端的设计系统决定。

### 10.3 控件响应的后台逻辑

#### 10.3.1 交互闭环全景

```
① Agent 生成 UI（含 action 定义）
    ↓  surfaceUpdate（组件带 action.name）
② 客户端原生渲染
    ↓  用户点击按钮
③ 客户端捕获交互，回传 userAction
    ↓  userAction（含 action.name + 参数）
④ Agent 接收，执行后台逻辑
    ↓  调用 Tools / MCP / A2A / 直接 HTTP
⑤ Agent 返回新的 A2UI 消息
    ↓  dataModelUpdate（更新数据）或 surfaceUpdate（更新 UI）
⑥ 客户端响应式更新
```

#### 10.3.2 Action 定义：控件如何"声明"自己被触发

交互组件通过 `action` 字段声明触发行为：

```json
{
  "id": "submit-btn",
  "component": "Button",
  "text": "确认预订",
  "action": { "name": "confirm_booking" }
}
```

- `action.name`：动作名称（如 `confirm_booking`、`cancel`、`select_item`）
- 当用户点击按钮时，客户端将 `action.name` + 相关参数封装为 `userAction` 回传 Agent

#### 10.3.3 数据绑定：控件状态如何与数据模型联动

A2UI 用 **JSON Pointer 路径**（RFC 6901）实现 UI 与数据分离：

```json
// 字面值（固定，不随数据变化）
{ "text": { "literalString": "欢迎" } }

// 数据绑定（响应式，随数据模型变化自动更新）
{ "text": { "path": "/user/name" } }
```

当 Agent 发送 `dataModelUpdate` 更新 `/user/name` 时，所有绑定该路径的组件**自动更新**——无需重新生成组件树。

```json
{
  "updateDataModel": {
    "surfaceId": "booking",
    "path": "/booking/date",
    "value": "2026-08-15"
  }
}
```

#### 10.3.4 后台逻辑的四种实现方式

A2UI **只负责 UI 层**，业务逻辑由 Agent 通过以下方式实现：

| 方式 | 场景 | 实现 |
|------|------|------|
| **内置 Tools（函数调用）** | Agent 内部逻辑 | Agent 收到 `confirm_booking` action → 调用 `book_restaurant()` 函数 → 操作数据库 |
| **MCP 服务器** | 标准化工具协议 | Agent 通过 MCPClient 调用 `create_booking` 工具 → MCP Server 执行 API 调用 |
| **A2A 委托** | 多 Agent 协作 | 主 Agent 收到 action → 通过 A2A 委托给专业预订 Agent → 子 Agent 返回结果 |
| **直接 HTTP/gRPC** | 简单集成 | Agent 直接调用外部 REST API |

**Agent 端处理 action 的代码示例**：

```python
async def handle_user_action(action: dict, surface_id: str):
    action_name = action["name"]

    if action_name == "confirm_booking":
        # 1. 执行后台业务逻辑（调用工具/MCP/A2A）
        booking_result = await book_restaurant(
            date=get_data_model_value(surface_id, "/booking/date"),
            guests=get_data_model_value(surface_id, "/booking/guests"),
        )

        # 2. 根据结果生成新的 A2UI 消息
        if booking_result.success:
            # 更新数据模型 → 绑定该路径的组件自动更新
            yield {
                "updateDataModel": {
                    "surfaceId": surface_id,
                    "path": "/booking/status",
                    "value": "预订成功！确认号: " + booking_result.confirmation_code
                }
            }
        else:
            # 更新 UI 结构（显示错误提示）
            yield {
                "updateComponents": {
                    "surfaceId": surface_id,
                    "components": [
                        {"id": "error-msg", "component": "Text",
                         "text": booking_result.error, "variant": "caption"}
                    ]
                }
            }
```

#### 10.3.5 响应式更新：两种更新策略

| 策略 | 消息类型 | 适用场景 | 效率 |
|------|----------|----------|------|
| **数据更新** | `dataModelUpdate` | 只改数据不改结构（如状态文字、列表内容） | 高（只传变更路径，绑定组件自动更新） |
| **结构更新** | `surfaceUpdate` / `updateComponents` | 增删组件或改属性（如显示/隐藏错误提示） | 中（按组件 ID 增量更新，非全量重建） |

> **性能优化**：A2UI 支持按 ID 精准更新单个组件，客户端做 diff 后只重渲染变更部分，适配 16ms 渲染周期。

#### 10.3.6 目录中的 Functions：可被 Agent 直接调用的函数

目录除了定义 `components`，还可定义 `functions`——这些是**Agent 可以直接调用的服务端函数**，扩展了纯 action 回传的能力：

```json
{
  "functions": [
    {
      "name": "search_restaurants",
      "description": "根据位置和菜系搜索餐厅",
      "parameters": {
        "type": "object",
        "properties": {
          "location": { "type": "string" },
          "cuisine": { "type": "string" }
        },
        "required": ["location"]
      }
    }
  ]
}
```

Agent 在生成 UI 时可调用这些函数获取数据，再将结果通过 `dataModelUpdate` 填充到 UI 中——形成"函数调用 → 数据填充 → UI 渲染"的闭环。

### 10.4 小结：大模型 × A2UI 的完整心智模型

```
┌──────────────────────────────────────────────────────┐
│  大模型（LLM）                                         │
│  ┌──────────────────────────────────────────────┐   │
│  │ System Prompt 注入：                           │   │
│  │  • A2UI 协议规则（邻接表、消息类型、ID 引用）   │   │
│  │  • 组件目录 Schema（JSON Schema，LLM 天然理解）│   │
│  │  • 数据绑定规则（literalString vs path）       │   │
│  │  • 输出格式（JSONL 流）                        │   │
│  └──────────────────────────────────────────────┘   │
│  ↓ 输出符合 Schema 的 JSONL                           │
├──────────────────────────────────────────────────────┤
│  Agent（业务逻辑层）                                   │
│  • 两阶段验证（发送前 + 客户端接收后）                  │
│  • 接收 userAction → 调用 Tools/MCP/A2A/HTTP          │
│  • 返回 dataModelUpdate 或 updateComponents           │
├──────────────────────────────────────────────────────┤
│  传输层（SSE / WebSocket / A2A / AG-UI）              │
├──────────────────────────────────────────────────────┤
│  客户端（渲染层）                                      │
│  • 目录协商（三步握手，取交集）                         │
│  • WidgetRegistry 组件白名单渲染                       │
│  • 主题/样式由宿主应用控制（Agent 不指定样式）          │
│  • 捕获用户交互 → 封装 userAction → 回传 Agent         │
│  • 优雅降级（未知组件占位、验证失败报错）                │
└──────────────────────────────────────────────────────┘
```

| 问题 | 答案 |
|------|------|
| **大模型如何理解 A2UI？** | 不靠"学框架"，靠读 JSON Schema——目录 Schema 注入 system prompt，LLM 像调用函数一样选用组件并填充属性；邻接表 + 流式 JSONL 让生成更轻松 |
| **如何自定义风格/控件？** | ① 定义目录 Schema（components + theme + functions）；② 客户端实现渲染器（React/Angular/Flutter）；③ 扩展基础目录（全量/挑选/完全自定义）。风格控制权在客户端，Agent 只描述结构不指定样式 |
| **控件响应的后台逻辑？** | 组件 `action.name` 声明触发行为 → 用户交互后客户端回传 `userAction` → Agent 通过 Tools/MCP/A2A/HTTP 执行业务逻辑 → 返回 `dataModelUpdate`（数据更新）或 `updateComponents`（结构更新）→ 客户端响应式重渲染 |
