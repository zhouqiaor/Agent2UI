## 第一部分：Git 检视工作流最佳实践

### 一、分支模型对比

| 模型 | 流程 | 适用场景 | 优势 | 劣势 |
|------|------|---------|------|------|
| **GitHub Flow** | main ← feature branch → PR → Review → Merge | 持续交付、小团队 | 简单、快速、基于主干 | 无正式发布分支 |
| **GitFlow** | develop ← feature → release → hotfix → main | 版本驱动发布、大团队 | 分支清晰、支持并行版本 | 分支多、管理复杂 |
| **Trunk-Based** | 所有开发在 trunk/main，短生命周期 feature branch | CI/CD 成熟、高成熟度团队 | 简单、快速、适合 CI | 依赖特性 Flag、需严格纪律 |

### 二、PR 尺寸与审查效率

| PR 规模 | 文件变更 | 代码行数 | 审查时间 | 建议 |
|---------|---------|---------|---------|------|
| **小型** | < 5 文件 | < 100 行 | < 5 分钟 | ✅ 最佳尺寸，优先处理 |
| **中型** | 5-15 文件 | 100-400 行 | 5-15 分钟 | ✅ 可接受，需专注核心变更 |
| **大型** | 15-30 文件 | 400-800 行 | 15-30 分钟 | ⚠️ 建议拆分 |
| **巨型** | > 30 文件 | > 800 行 | > 30 分钟 | ❌ 必须拆分 |

### 三、Android/Kotlin 审查清单

#### 3.1 正确性
- [ ] 所有 `sealed class` / `sealed interface` 分支已在 `when` 中处理（编译器强制）
- [ ] `StateFlow` / `SharedFlow` 生命周期正确
- [ ] 协程作用域（`viewModelScope` / `lifecycleScope`）使用正确
- [ ] 数据流正确处理异常（`catch` / `recover`）
- [ ] 无 `GlobalScope` 使用
- [ ] 线程安全：`MutableStateFlow` 从 `IO` 线程更新时使用 `tryEmit`

#### 3.2 可维护性
- [ ] 函数长度 < 50 行（复杂逻辑拆分）
- [ ] 类职责单一（SRP 原则）
- [ ] 命名清晰：变量/函数/类名自解释
- [ ] 无魔法数字/字符串（定义常量）
- [ ] 数据类字段 `@Immutable` 标注
- [ ] 密封类/接口穷举所有分支

#### 3.3 性能
- [ ] Compose 稳定性：参数传递 `@Stable` / `@Immutable` 类型
- [ ] 避免在 `@Composable` 内创建对象（`derivedStateOf` 优化派生状态）
- [ ] `LazyColumn` / `LazyRow` 提供 `key` 和 `contentType`
- [ ] Flow 使用 `distinctUntilChanged()` / `conflate()` 过滤
- [ ] Room 查询有索引，大数据量使用 Paging 3
- [ ] 图片加载合理配置缓存策略

#### 3.4 安全性
- [ ] 无硬编码密钥/密码/Token
- [ ] 敏感数据不在 Log 中输出
- [ ] `WebView` 开启安全模式
- [ ] HTTPS 强制，证书锁定
- [ ] 输入验证与清理

### 四、自动化审查工具集成

| 工具 | 用途 | 集成方式 |
|------|------|---------|
| **Danger** | PR 尺寸检查、规则引擎 | GitHub Actions + Dangerfile |
| **detekt** | Kotlin 静态代码分析 | Gradle 插件 + CI 任务 |
| **ktlint** | Kotlin 代码格式化 | Gradle 插件 + pre-commit hook |
| **Baseline Profile Generator** | Compose 基准配置生成 | Androidx 库 + Release 构建 |
| **Lint** | Android 代码检查 | 内置 Gradle 任务 |
| **jacoco** | 代码覆盖率 | Gradle + CI 报告 |

### 五、审查绩效模型

```
Produce（产出）→ Review（审查）→ Recycle（再生）
     ↓               ↓              ↓
 开发者提交      审查者审核     开发者修改
 5% 代码          10% 时间      85% 学习
```

**关键指标**:
- **PR 吞吐量**: 每 reviewer 每小时审查 3-5 个中型 PR
- **首次审查响应时间**: < 2 小时（上班时间）
- **审查轮次**: 平均 2-3 轮通过
- **Bug 捕获率**: 代码审查可捕获 60-90% 的缺陷

## 第二部分：多 Agent 协作模式

### 六、多 Agent 框架对比

| 维度 | AutoGen (Microsoft) | LangGraph (LangChain) | CrewAI | MetaGPT | AGenUI |
|------|--------------------|----------------------|--------|---------|--------|
| **核心模式** | 对话式 Agent 会话 | 有状态图工作流 | 角色驱动协作 | 软件公司模拟 | A2UI 生成流水线 |
| **Agent 类型** | ConversableAgent | StateGraph Node | Role Agent | SWEAgent/PM | A2UI Generator |
| **通信方式** | 消息传递 | 图边 + 共享状态 | 顺序/层级 | 层级对话 | A2A 协议 |
| **状态管理** | 内存会话 | 持久化 Checkpoint | 会话历史 | 任务列表 | A2UI Surface |
| **人类介入** | 支持（`human_input_mode`） | 支持（中断节点） | 支持 | 支持 | 支持（等待用户输入） |
| **A2UI 适配** | 需适配 | ✅ 天然适配 | 需适配 | 需适配 | ✅ 原生 A2UI |
| **成熟度** | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐ |
| **Python 支持** | ✅ | ✅ | ✅ | ✅ | ❌ (C++/Kotlin) |
| **移动端适配** | 需服务端 | 需服务端 | 需服务端 | 需服务端 | ✅ 原生 SDK |

### 七、协作模式分类

| 模式 | 说明 | 框架 | 适用场景 |
|------|------|------|---------|
| **顺序管道** | Agent A → Agent B → Agent C 串行执行 | AGenUI、LangGraph | spec → design → code → test |
| **并行审议** | 多个 Agent 同时审视同一问题，互相质询 | AutoGen | 多视角审查、质量保证 |
| **层级协作** | 上级 Agent 分解任务，下级 Agent 执行汇报 | CrewAI、MetaGPT | 产品→架构→代码角色链 |
| **图状态机** | 复杂工作流用图表示，支持分支和合并 | LangGraph | 多步审批、条件分支 |
| **对抗博弈** | Agent A 生成，Agent B 挑战，Agent A 辩护 | AutoGen Debate | 安全审计、红队演练 |

## 第三部分：A2UI 代码检视流程

### 九、三层闸门检视架构

```
PR 提交
  │
  ▼
┌─────────────────────────────────────────┐
│  第一层：自动化门禁（CI/CD）              │
│  ├── 构建检查（Gradle assemble）          │
│  ├── 静态分析（detekt + ktlint + Lint）   │
│  ├── 测试覆盖率（jacoco ≥ 80%）           │
│  ├── Baseline Profile 检查               │
│  └── PR 尺寸检查（Danger < 400 行）       │
│  结果：✅ 通过 → 进入第二层 / ❌ 打回修改   │
└─────────────────────────────────────────┘
  │ ✅
  ▼
┌─────────────────────────────────────────┐
│  第二层：多 Agent 并行审查               │
│  ├── Agent 1: 正确性审查                 │
│  ├── Agent 2: 安全性审查（OWASP Top 10） │
│  ├── Agent 3: 性能审查（Compose 稳定性）  │
│  ├── Agent 4: 代码风格审查               │
│  └── Agent 5: A2UI 协议合规审查          │
│  结果：所有 Agent ⚠️/✅ → 进入第三层      │
│         任何 Agent ❌ → 打回修改          │
└─────────────────────────────────────────┘
  │ ⚠️/✅
  ▼
┌─────────────────────────────────────────┐
│  第三层：人工审批                        │
│  ├── Tech Lead 架构审查                  │
│  ├── 设计一致性审查                      │
│  └── 最终批准 / 修改请求                 │
│  结果：✅ 合并 / ❌ 修改                  │
└─────────────────────────────────────────┘
```

### 十、A2UI 协议合规审查要点

| 审查项 | 说明 | 检查方法 |
|--------|------|---------|
| **组件白名单** | 仅允许 Catalog 定义的组件类型 | Schema 验证 |
| **Design Token** | 颜色/字体/间距使用 Token 而非硬编码 | Token 映射检查 |
| **安全边界** | 无 `execute` / `eval` 等危险操作 | 静态分析 |
| **流式协议** | JSONL 格式正确，增量更新有效 | 协议校验 |
| **状态一致性** | `surfaceId` / `dataModel` / `userAction` 一致 | 跨层检查 |

### 十一、冲突解决机制

#### Agent 冲突决策矩阵

| 冲突类型 | 决策规则 | 示例 |
|---------|---------|------|
| 正确性 vs 性能 | 正确性优先 | "应该用 `StateFlow` 而非 `SharedFlow`" |
| 性能 vs 可读性 | 可读性优先（除非性能瓶颈） | "内联 vs 提取变量" |
| 风格 vs 风格 | 多数 Agent 投票 | "命名：`user` vs `account`" |
| 安全 vs 便利 | 安全优先 | "加密存储 vs 明文存储" |
| A2UI 协议 vs 代码质量 | 协议优先 | "必须使用 A2UI 组件而非自定义" |

#### 四级升级机制

```
Level 1: 自动解决（Agent 内部规则）
Level 2: 多数投票（所有审查 Agent 投票）
Level 3: 人工裁决（Tech Lead 决策）
Level 4: 架构师决策（需架构评审委员会批准）
```

| 周次 | 阶段 | 任务 | 产出 |
